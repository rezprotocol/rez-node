# Running a Rez Node

This guide covers how to self-host a Rez node — either as a combined chat-server-plus-relay, or as a standalone relay node contributing to the mesh.

---

## Modes

| Mode | What it does |
|---|---|
| **Embedded** (default) | `rez-chat` starts a full `rez-node` in-process. Easiest for personal use. |
| **Standalone node** | `rez-node start` runs as a dedicated server. Use for shared family/team hosting. |
| **Relay-only** | A node that participates in mesh routing but does not serve chat clients directly. |

---

## Option 1: Embedded via rez-chat

The default `rez-chat` startup embeds a full node automatically. No separate process needed.

```bash
# Start with defaults (port 3000, node WS on 8787)
node rez-chat/src/index.js

# With custom ports
CHAT_PORT=8080 REZ_NODE_WS_PORT=9000 node rez-chat/src/index.js
```

**Configuration** is loaded from `rez.config.json` in the working directory (created on first run):

```json
{
  "node": {
    "ws": {
      "port": 8787,
      "path": "/ws"
    },
    "storage": {
      "dataDir": ".local/rez-node-data"
    },
    "network": {
      "participateInRouting": true,
      "knownRelays": []
    }
  }
}
```

### Environment variables (rez-chat)

| Variable | Default | Description |
|---|---|---|
| `CHAT_PORT` | `3000` | HTTP port for the chat web UI |
| `CHAT_BIND_HOST` | `0.0.0.0` | Host to bind the HTTP server |
| `REZ_NODE_WS_PORT` | `8787` | WebSocket port for the embedded node |
| `REZ_NODE_DATA_DIR` | `.local/rez-node-data` | Node storage directory |
| `REZ_CHAT_CONFIG_PATH` | `./rez.config.json` | Config file path override |
| `REZ_CHAT_DISABLE_NODE` | — | Set to `1` to skip embedded node (use `REZ_CHAT_WS_URL` instead) |
| `REZ_CHAT_WS_URL` | — | External node WS URL when `DISABLE_NODE=1` |

## Option 2: Standalone rez-node

### Install

```bash
npm install -g @rezprotocol/node
```

Or run from the monorepo:

```bash
node rez-node/src/cli/index.js
```

### Initialize

```bash
rez-node init
```

This creates `rez-node.config.json` and `.local/rez-node-data/` in the current directory. Review and edit the config before starting.

### Validate

```bash
rez-node doctor
```

Checks config validity, storage accessibility, and network reachability.

### Start

```bash
rez-node start
```

### CLI reference

```
rez-node version                        Print version
rez-node init [--config <path>]         Initialize config and data dir
             [--data-dir <path>]
             [--force]                  Overwrite existing config
rez-node doctor [--config <path>]       Validate setup
rez-node start  [--config <path>]       Start node
                [--no-control]          Disable control socket
```

### Full config reference

```json
{
  "node": {
    "mode": "full",
    "ws": {
      "host": "127.0.0.1",
      "port": 8787,
      "path": "/ws"
    },
    "network": {
      "knownRelays": []
    },
    "mesh": {
      "mode": "seeded-gossip",
      "seeds": [],
      "minPeers": 3,
      "maxPeers": 32,
      "discoveryIntervalMs": 30000,
      "gossipIntervalMs": 60000,
      "policy": {
        "rateLimit": 120,
        "payloadMaxBytes": 1048576,
        "failureThreshold": 8
      }
    },
    "storage": {
      "dataDir": "./.local/rez-node-data",
      "defaultThreadId": "<auto-generated>"
    },
    "backup": {
      "retentionDays": 90
    }
  }
}
```

## Option 3: Relay-only Node

A relay-only node participates in the mesh for routing and inbox hosting but does not serve chat clients.

```json
{
  "node": {
    "mode": "relay-only",
    "relay": {
      "advertisedHost": "relay.example.com",
      "listenPort": 4201,
      "listenHost": "0.0.0.0",
      "relayKeyId": "relay_a",
      "directory": {
        "enabled": true,
        "host": "127.0.0.1",
        "port": 4100
      }
    },
    "mesh": {
      "mode": "seeded-gossip",
      "seeds": ["tls://relay1.example.com:4201"],
      "minPeers": 3,
      "maxPeers": 32
    },
    "storage": {
      "dataDir": "/var/lib/rez/relay-a"
    }
  }
}
```

```bash
rez-node start --config relay.config.json --no-control
```

## Directory Service

The directory service provides HTTP endpoints for relay descriptor discovery. Clients use it to find relays to route through.

When `relay.directory.enabled: true`, `rez-node` starts the directory server automatically on the configured host/port.

```bash
# Standalone directory (from rez-node package)
rez-directory --bind 127.0.0.1 --port 4100
```

Clients discover relays by querying:

```
GET http://directory.example.com:4100/relays
```

## Hosted Docker cluster

The supported multi-node deployment is `deploy/docker-compose.yml`: two node identities behind a
non-sticky TLS WebSocket load balancer, with shared Postgres and Redis. See
[RUN_A_CLUSTER.md](./RUN_A_CLUSTER.md). Live source-mesh proof remains available as the explicit
`RUN_LOCAL_MESH_E2E=1` node test; there are no hidden `docker/reznet*` directories.

## Firewall / Port Requirements

| Component | Protocol | Default Port | Required open? |
|---|---|---|---|
| Chat web UI | HTTP | 3000 | Depends (local vs. public) |
| Node WebSocket gateway | WS/TCP | 8787 | Only if clients connect remotely |
| Relay TCP mesh | TCP/TLS | 4201+ | Yes, for relay participation |
| Directory service | HTTP | 4100 | Yes, for relay discovery |

For a personal node used only locally, no ports need to be externally exposed.

## Data Directory Layout

```
.local/rez-node-data/
├── identity/               Node identity keypair and account

├── relay/                  Relay state (peer keys, routing table)
├── kv/                     Key-value store (app namespace)
├── objects/                Object store (blobs, backups)
└── control.sock            Control socket (Unix / named pipe)
```

## Relay Economics / Earning

Running a relay is **permissionless**: anyone may stand up a node and carry traffic, today, with no allowlist and no token-denominated bond or stake. Core encrypted messaging is **free** and stays that way — relaying it costs you resources and earns you nothing directly, by design. Earning enters the picture as paid services and trust-graph recognition come online; this is a permissionless *and* an earning network, not a volunteer mesh.

**Fee revenue (paid services).** Paid services — memorable `@handles`, persistent storage, large files, content hosting — are the things that cost a relay real resources, and they generate fee revenue for the serving relay. They flow through the node's `ServiceGate` (capability → price → atomic multi-leg `settleService`) backed by a `SettlementProvider`. In beta this is `LocalSettlementProvider` running on **off-chain credits**; chain mode uses `ChainSettlementProvider` and runs on **testnet only** until mainnet. A request against an underfunded balance is rejected with `PAYMENT_REQUIRED`; every settled service is recorded as a canonical `SettlementEntryV1` in the append-only `SettlementJournal`.

**REZ emissions (the 500M rewards pool).** Emissions are separate from fee revenue and are *not* paid to relays on mainnet today. Earning REZ from the rewards pool requires **trust-graph recognition** — an EigenTrust-style rank seeded from the published, neutral, multi-operator seed-relay set (the existing `knownRelays` mechanism is the bootstrap trust root). Rank is built only by sustained, real, counterparty-confirmed service over time; it **decays** and **saturates**. There is **no REZ-denominated bond and no staking** — the barrier is real service, never capital. Objective facts about yourself (disk, uptime) only make you *eligible*; rank and emissions require being demanded and vouched-for by other recognized relays. Emissions activate with relay↔relay demand later (Tier 4+) and pay out on mainnet (Tier 6).

**`networkId`.** An immutable, pre-genesis constant is bound into the signed body of every economic artifact your relay signs — settlement receipts, peer attestations, escrow records, relay descriptors, storage proofs. Only artifacts carrying the official `networkId` earn or convert, which cleanly isolates private forks.

**Relay eth key (chain mode).** Chain settlement mode (testnet in beta) uses a separate Ethereum key for on-chain operations, distinct from the node identity keypair. The chain-mode code is confined to `rez-node/src/settlement/eth/`. Back up and protect this key with the same care as the node identity; see the keystore guidance below.

## Security Notes

- The node WebSocket gateway (`127.0.0.1:8787`) should not be exposed publicly unless you intend to allow remote client connections. Bind to `127.0.0.1` for local-only use.
- Relay TCP endpoints should use TLS in production. Set `tls: true` in your relay endpoint config.
- The `dataDir` contains the node's identity keypair. Back it up securely — if lost, the relay's identity cannot be recovered.
- All client message content is E2EE; the node operator sees only ciphertext.
